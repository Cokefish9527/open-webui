# 外部后台管理系统对接测试方案

## 1. 概述

本文档详细说明如何测试外部后台管理系统与当前项目的对接功能，确保对接的安全性、功能完整性和稳定性。

## 2. 测试环境

### 2.1 硬件环境
- CPU: 2核或以上
- 内存: 4GB或以上
- 磁盘空间: 20GB或以上可用空间

### 2.2 软件环境
- 操作系统: Linux (Ubuntu 20.04+/CentOS 7+/Debian 10+) 或 Windows Server 2016+
- Python版本: 3.11+
- 数据库: PostgreSQL 12+ 或 SQLite 3.35+
- 测试工具: Postman/curl/JMeter

## 3. 测试准备

### 3.1 环境配置
1. 配置环境变量：
   ```env
   EXTERNAL_ADMIN_SECRET_KEY=test_secret_key
   EXTERNAL_ADMIN_IP_WHITELIST=127.0.0.1,192.168.1.100
   ```
2. 启动应用服务
3. 准备测试数据

### 3.2 测试工具准备
1. 安装Postman或准备curl命令
2. 准备测试脚本
3. 配置测试环境IP地址

## 4. 功能测试

### 4.1 用户管理测试

#### 4.1.1 创建用户测试
**测试目标**: 验证外部系统可以成功创建用户

**测试步骤**:
1. 准备创建用户请求数据
2. 发送POST请求到`/api/v1/external/admin/users`
3. 验证返回结果和数据库记录

**预期结果**:
- 返回200状态码
- 返回正确的用户信息
- 数据库中创建了对应的用户记录

**测试用例**:
```json
{
  "email": "test@example.com",
  "name": "测试用户",
  "password": "testpassword123",
  "role": "user",
  "profile_image_url": "/user.png"
}
```

#### 4.1.2 更新用户测试
**测试目标**: 验证外部系统可以成功更新用户信息

**测试步骤**:
1. 准备更新用户请求数据
2. 发送PUT请求到`/api/v1/external/admin/users/{user_id}`
3. 验证返回结果和数据库记录

**预期结果**:
- 返回200状态码
- 返回更新后的用户信息
- 数据库中用户信息已更新

**测试用例**:
```json
{
  "email": "updated@example.com",
  "name": "更新用户",
  "role": "admin",
  "profile_image_url": "/updated.png"
}
```

#### 4.1.3 删除用户测试
**测试目标**: 验证外部系统可以成功删除用户

**测试步骤**:
1. 发送DELETE请求到`/api/v1/external/admin/users/{user_id}`
2. 验证返回结果
3. 检查数据库中用户是否已删除

**预期结果**:
- 返回200状态码
- 返回删除成功消息
- 数据库中用户记录已删除

#### 4.1.4 获取用户列表测试
**测试目标**: 验证外部系统可以成功获取用户列表

**测试步骤**:
1. 发送GET请求到`/api/v1/external/admin/users?page=1&size=10`
2. 验证返回结果

**预期结果**:
- 返回200状态码
- 返回用户列表和分页信息

## 5. 安全测试

### 5.1 IP白名单测试

#### 5.1.1 允许IP访问测试
**测试目标**: 验证白名单内的IP可以正常访问

**测试步骤**:
1. 使用白名单内的IP地址发送请求
2. 验证请求是否被处理

**预期结果**:
- 请求被正常处理
- 返回正确的响应结果

#### 5.1.2 拒绝IP访问测试
**测试目标**: 验证白名单外的IP被拒绝访问

**测试步骤**:
1. 使用白名单外的IP地址发送请求
2. 验证请求是否被拒绝

**预期结果**:
- 返回403状态码
- 返回IP地址不在白名单中的错误信息

### 5.2 请求签名测试

#### 5.2.1 有效签名测试
**测试目标**: 验证正确签名的请求被接受

**测试步骤**:
1. 生成正确的请求签名
2. 发送带签名的请求
3. 验证请求是否被处理

**预期结果**:
- 请求被正常处理
- 返回正确的响应结果

#### 5.2.2 无效签名测试
**测试目标**: 验证错误签名的请求被拒绝

**测试步骤**:
1. 生成错误的请求签名
2. 发送带错误签名的请求
3. 验证请求是否被拒绝

**预期结果**:
- 返回401状态码
- 返回签名验证失败的错误信息

### 5.3 时间戳验证测试

#### 5.3.1 有效时间戳测试
**测试目标**: 验证在有效时间范围内的请求被接受

**测试步骤**:
1. 生成当前时间戳
2. 发送带时间戳的请求
3. 验证请求是否被处理

**预期结果**:
- 请求被正常处理
- 返回正确的响应结果

#### 5.3.2 过期时间戳测试
**测试目标**: 验证过期时间戳的请求被拒绝

**测试步骤**:
1. 生成过期时间戳（超过5分钟）
2. 发送带过期时间戳的请求
3. 验证请求是否被拒绝

**预期结果**:
- 返回401状态码
- 返回请求已过期的错误信息

## 6. 性能测试

### 6.1 并发访问测试
**测试目标**: 验证系统在高并发情况下的稳定性

**测试步骤**:
1. 使用JMeter等工具模拟并发请求
2. 监控系统响应时间和资源使用情况
3. 检查系统是否出现错误

**预期结果**:
- 系统响应时间在可接受范围内
- 无资源泄漏
- 无请求失败

### 6.2 大数据量测试
**测试目标**: 验证系统在大数据量情况下的性能

**测试步骤**:
1. 创建大量测试数据
2. 执行查询和管理操作
3. 监控系统性能指标

**预期结果**:
- 系统性能无明显下降
- 查询响应时间在可接受范围内

## 7. 异常测试

### 7.1 参数验证测试
**测试目标**: 验证系统对无效参数的处理

**测试步骤**:
1. 发送包含无效参数的请求
2. 验证系统返回的错误信息

**预期结果**:
- 返回400状态码
- 返回详细的参数验证错误信息

### 7.2 数据一致性测试
**测试目标**: 验证系统在异常情况下的数据一致性

**测试步骤**:
1. 模拟网络中断等异常情况
2. 检查数据库中数据的一致性

**预期结果**:
- 数据库中数据保持一致
- 无数据丢失或损坏

## 8. 回归测试

### 8.1 现有功能验证
**测试目标**: 确保新功能不影响现有系统功能

**测试步骤**:
1. 执行所有现有的测试用例
2. 验证系统功能是否正常

**预期结果**:
- 所有现有功能正常工作
- 无功能退化

## 9. 测试执行计划

| 测试阶段 | 测试内容 | 预计时间 | 负责人 |
|---------|---------|---------|-------|
| 第1天 | 环境准备和基础功能测试 | 4小时 | 测试团队 |
| 第2天 | 安全测试 | 4小时 | 安全团队 |
| 第3天 | 性能测试 | 4小时 | 运维团队 |
| 第4天 | 异常测试和回归测试 | 4小时 | 测试团队 |
| 第5天 | 测试报告编写 | 2小时 | 测试团队 |

## 10. 测试通过标准

1. 所有功能测试用例通过率100%
2. 所有安全测试用例通过率100%
3. 性能测试指标满足要求
4. 无严重或高危安全漏洞
5. 代码覆盖率不低于80%

## 11. 风险评估

| 风险项 | 影响程度 | 应对措施 |
|-------|---------|---------|
| 安全验证逻辑错误 | 高 | 增加边界测试用例 |
| 数据一致性问题 | 高 | 增加事务完整性测试 |
| 性能下降 | 中 | 优化查询逻辑，增加索引 |
| 兼容性问题 | 中 | 在多环境下进行测试 |
